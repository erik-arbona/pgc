# dsd

**Responsibility:** the DSD module (functional block 6, load calculation and validations). For now only pure domain rules; the models (DSD, offerings, teaching units, assignments) arrive with the phase 2 tasks T2.1 onwards.

**Rules (pure Python, no Django):**
- `teaching_hours.semester_teaching_hours` – weekly and semester teaching hours of each teacher: weekly hours of the class type x the teacher's share / 100, summed. A merged class is one teaching unit and counts once; each group is one unit, so N groups count N times. Exact `Decimal` arithmetic on the lines; only the totals of a teacher are rounded to two decimals, half up (D73). Returns the lines that explain each number and the share total of each unit for the alerts. See D70.
- `preparation.teacher_preparation_hours` / `preparation_by_teacher` – weekly preparation hours of each teacher: the weights per class type (`academic.preparation`) applied to the teacher's weekly hours, so preparation follows each lesson hour (repeated per group, per share). See D71.
- `annual_load.annual_teaching_hours` / `annual_load` – annual weekly teaching hours (sum of the two semesters, with each semester kept) joined with the range in force on a reference date given by the caller (`staff.load_ranges.resolve_load_range`). The four states and the extra hours come next. See D72.
- `load_status.assess_load` – the state of the annual load (below the minimum, in the range, at the maximum, above the maximum, or no range) and the extra hours (total minus the maximum above it), from the annual load. See D74.

**Dependencies:** `academic.preparation` and `staff.load_ranges` (pure functions); nothing else yet (the Django adapter will use `academic`, `staff` and `core.parameters`).

**Models (T2.1):** `Dsd` (one per academic year for the whole University, `OneToOne` with `AcademicYear`) and `DsdSemester` (semesters 1 and 2, created together with the DSD). `services.create_dsd` creates both in one transaction and turns the database constraint into the message «Já existe um DSD para o ano letivo X.», also when two managers create it at the same time. Screens: `/dsd/` (list, manager and coordinator) and `/dsd/new/` (manager only). See D85.

**State of the semesters (T2.2):** `CoordinationSemester` holds the state (open or closed) of a semester for a coordination; no row means "not opened". `lifecycle_rules.next_state` is the pure table of moves; `services.change_state` opens, closes or reopens many cells in one transaction (skipped cells are reported, one audit entry per changed cell). `lifecycle.dsd_write` is the write guard (scope check, row lock, closed = read-only, not opened = manager only) and `GuardedDsdWrites` makes any future DSD model fail if it is saved outside it. Screens: `/dsd/<id>/` (grid) and `/dsd/<id>/state/` (manager only). See D86.

**Offerings (T2.3a):** `Offering` (one per DSD semester and subject, owned by the subject's coordination) and `OfferingClassGroup` (the turmas that take it, a snapshot that keeps the history). `services.generate_offerings` adds what is missing from the turmas and their plans (curricular year, semester, tracks), never deletes, reports stale rows, skips closed cells and coordinations the manager does not cover. Both models inherit `GuardedDsdWrites` (`guard.py`) and are written inside `dsd_write`. Screens: `/dsd/<id>/offerings/` and `/dsd/<id>/offerings/generate/`. See D87.

**Regente (T2.3b):** `services.set_lead_teacher` sets, changes or clears `Offering.lead_teacher`: an active teacher of the subject's coordination, written inside `dsd_write`, with the optimistic lock (the version the user saw), a reason when there already is one and an audit entry. Screen: `/dsd/offerings/<id>/lead-teacher/`, linked from the offerings list. See D88.

**Teaching units (T3.1a):** `TeachingUnit` (offering x class type, optimistic lock) and `TeachingUnitMember` (the turmas of the offering that attend it; a unique constraint keeps one whole-turma unit per turma and class type). `generate_offerings` also creates the default units (one per turma and class type of the subject's loads), idempotently and in a savepoint per unit, and counts the stale ones without deleting. Hours are derived from the subject's loads, not stored. See D89.

**Offering page (T3.1b):** `/dsd/offerings/<id>/` shows one row per teaching unit (class type, weekly hours read from the subject's loads, turmas, size as the sum of the turmas marked provisional while estimated, and a mark when the unit is stale). `services.stale_unit_ids` gives the stale units of a cell, the same set that the generation counts. Read-only: manager and coordinator. See D89.

**Groups (T3.2a):** `SubGroup` (a turma of an offering x a class type x a number from 1). Each group is its own teaching unit; the audience of a unit (`TeachingUnitMember`) is a whole turma or a group (a database check), and a group belongs to one unit only. `services.set_group_count` divides a turma into N groups for a class type, grows or shrinks N, or goes back to the whole turma, inside `dsd_write` with the action `dsd.teaching_unit.edit`, a row lock on the turma link and the unit versions the user saw. The generator keeps the whole-turma unit away from a divided turma and flags the group units whose turma left. See D90.

**Group screens (T3.2b):** `/dsd/offerings/<id>/groups/<turma link>/<class type>/` divides a turma into N groups or changes N (`services.set_group_count`, reason required when already divided, unit versions in a hidden field). The offering page shows 'Dividir em grupos' or 'Alterar n.º de grupos' only to who can write the cell (`lifecycle.cell_writable`, the read-only twin of `dsd_write`). See D90.

**Merges (T3.3a):** `services.merge_units` joins two or more units of one offering and class type into one (the host keeps every member, the others are deleted); `services.separate_member` takes a member out into a unit of its own. A merge needs the sum of the students (a group counts as turma / groups rounded up, `sizes.group_students`) to fit some room of the campus, checked with `rooms.room_summary` quantities only (the coordinator never sees a room, D64); the coordinator states the room capacity (and optionally type) asked, saved on the unit as `room_capacity` / `room_type` (a request, not a booking). Rows are locked by id and the unit versions the user saw are compared. See D91.

**Merge screens (T3.3b):** the offering page selects units with checkboxes and sends them by GET to `/dsd/offerings/<id>/merge/`, which shows the members, the sum of the students and (only to who may read rooms) room quantities, and asks for the room capacity and type (the sum is suggested), an optional reason and the versions seen. `/dsd/offerings/<id>/units/<unit>/separate/<member>/` takes a member out with a required reason. Row buttons come from `OfferingDetailView._actions`. See D91.

**Cross-course merges (T3.4a):** `merge_units` also merges units of different offerings when the subjects are transversal to each other (same cross-course group, plan in force, indicated courses), of the same semester, class type and coordination (Q8). The hours count under the host's subject; `merge_load_differences` lists the weekly hours of each subject when they differ and the merge then needs `accept_load_difference`. `_stale_unit_ids` checks each member against its own subject and flags a cross-course merge that stopped being valid. `separate_member` returns a member to a unit of its own offering and keeps one own turma in the host. See D92.

**Cross-course screens (T3.4b):** the offering page of a transversal subject lists the units of the partner offerings (`services.partner_offerings`) to select, and shows where its turmas were merged (`services.guest_members`). The merge page takes units of any offering of the same DSD semester, lets the coordinator choose the host and, when the weekly load differs, asks to confirm. The groups button of a turma of another course points at that turma's own offering. See D92.

**Room request (T3.5):** `services.set_room_request` sets, changes or clears the capacity (and optional room type) a teaching unit asks for, inside `dsd_write`, with the unit version the user saw and a reason when changing. `services.room_request_warnings` says, when the page is shown, whether no room of the campus fits (via `rooms.room_summary` quantities) or the capacity is below the unit's students (`services.unit_students`); it warns and never blocks, except when merging. Screen: `/dsd/offerings/<id>/units/<unit>/room/`. See D93.

**Teacher of a unit (T5.1a):** `TeachingUnit.teacher` is the only teacher of a unit; there is no sharing and no percentage (D94). `services.assign_teacher` / `unassign_teacher` give, replace or remove it inside `dsd_write` with the action `dsd.assignment.edit` and the unit version the user saw: an active teacher of the subject's coordination, not on an obsolete unit, with a reason to replace or remove. `merge_units` refuses more than one teacher and keeps the one the host has; `separate_member` leaves the new unit without teacher; `set_group_count` refuses to divide or drop a unit that has one. The live hours and load come in T5.1b. See D94.

**Live load and teacher screens (T5.1b):** `load_facts.unit_facts` turns the taught units of a semester into the facts of the hours rule (hours of the unit's own offering subject; units without hours are returned apart) and `load_facts.teacher_loads` gives, for some teachers, the annual hours, the state and extra hours, and the weekly preparation of each semester, computed when asked with a fixed number of queries. The offering page shows each unit's teacher with the state of their load; `/dsd/offerings/<id>/units/<unit>/teacher/` gives, changes or removes the teacher (action `dsd.assignment.edit`) and shows the load each candidate would have. See D94.

**Other activities (T5.3):** `OtherActivity` holds the non-teaching component of a teacher per semester (kind, description, weekly hours); `add_activity`, `edit_activity` and `remove_activity` write it through `dsd_write` with `dsd.assignment.edit`, the cell being the semester and the coordination stored with the activity. `other_activities` has the pure rules (sum by semester and the general total); `load_facts.TeacherLoad` now carries `other_hours` and `general_total`, while the range still checks only the teaching hours. The sheet is `/dsd/<dsd>/teachers/<teacher>/`. See D95.

**Overview of a coordination (T6.1):** `overview` has the pure rules (`attention_items` and `load_bar`); `coordination_overview.coordination_overview` reads the units of a semester and the live load of the teachers and returns what the screen draws; `CoordinationOverviewView` serves `/dsd/<dsd>/coordinations/<coordination>/` (action `dsd.coordination.view`, scoped by coordination). Tenders and deadlines are not shown because they do not exist yet. See D98.

**Assignment by subject (T6.2):** the offering page marks the units still to assign and, where the user may write the cell, offers a teacher selector in the row (`teacher_choices` gives the candidates and their load, shared with the unit form). `UnitTeacherInlineView` takes the choice by POST, answers with the updated row for HTMX or redirects without it, and only gives a teacher to a unit that has none. See D99.
